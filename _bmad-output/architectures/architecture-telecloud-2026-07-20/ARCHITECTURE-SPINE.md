# Architecture Spine — TeleCloud R2 Storage Integration

## Design Paradigm

**Pluggable storage adapter** — the application talks to storage through `IStorageProvider`, a single interface with two implementations: `LocalDiskStorageProvider` (deprecated, backward compat only) and `R2StorageProvider`. The adapter decides mechanics (chunk vs object, stream vs redirect) inside the implementation; application code never knows which backend is active.

The storage adapter sits inside the existing **CQRS** architecture: FastEndpoints handle HTTP, Wolverine routes commands/queries, handlers call `IStorageProvider`.

```
FastEndpoints ──→ Handler ──→ IStorageProvider
                    │               ├── R2StorageProvider (active)
                    │               └── LocalDiskStorageProvider (deprecated)
                    │
                    └── AppDbContext (metadata only)
```

## Inherited Invariants

| Inherited | From parent | Binds here |
| --- | --- | --- |
| CQRS via FastEndpoints + Wolverine | Existing codebase | R2 endpoints follow same pattern: Endpoint → IMessageBus → Handler |
| `IStorageProvider` abstraction | Existing codebase | R2StorageProvider implements same interface (extended) |
| ChunkId = `Guid.CreateVersion7()` | Existing codebase | R2 does not use chunk IDs — uses R2 object key instead |
| ShareCode-based delivery lookup | Existing codebase | Download routing unchanged |

## Invariants & Rules

### AD-1 — IStorageProvider extended with R2 methods

- **Binds:** CAP-1, CAP-2, CAP-3, CAP-4, CAP-5
- **Prevents:** Proliferation of two parallel storage abstractions
- **Rule:** `IStorageProvider` gains high-level R2 methods. `LocalDiskStorageProvider` throws `NotSupportedException` for all new methods. `[ADOPTED]`

### AD-2 — Separate upload start endpoints

- **Binds:** CAP-1, CAP-3
- **Prevents:** Discriminated response shapes in a single endpoint
- **Rule:** `POST /api/uploads/start-r2` returns `{uploadId, parts: [{partNumber, signedUrl}]}`. Old `POST /api/uploads/start` (returns `{uploadId, chunkSize}`) stays for backward compat. `[ADOPTED]`

### AD-2a — Client storage mode via config constant

- **Binds:** CAP-4
- **Prevents:** Runtime discovery overhead per upload
- **Rule:** Blazor WASM client reads storage mode at startup via config. No discovery endpoint. Deployment-time decision. `[ADOPTED]`

### AD-3 — DI registers R2StorageProvider directly

- **Binds:** CAP-4
- **Prevents:** Config-driven switching complexity
- **Rule:** `Program.cs` registers `R2StorageProvider` as `IStorageProvider`. `LocalDiskStorageProvider` marked `[Obsolete]`, not wired in DI for new deployments. `[ADOPTED]`

### AD-4 — R2 object key naming + auth gate

- **Binds:** CAP-1, CAP-3
- **Prevents:** Key collision across users; key format divergence between upload and download
- **Rule:** Object key = `uploads/{userId}/{deliveryId}/{fileName}`. Generated by a shared utility method `R2ObjectKey.For(userId, deliveryId, fileName)` — never constructed inline. `fileName` is URL-escaped (any `/`, `\`, or control char encoded). Only authenticated users can upload to R2 (auth gate already exists in `StartUploadHandler`). Anonymous users limited to P2P. `[ADOPTED]`

### AD-5 — High-level IStorageProvider methods

- **Binds:** CAP-1, CAP-2, CAP-3, CAP-5
- **Prevents:** Leaky abstractions exposing R2 API details to application code
- **Rule:** Interface methods group multiple R2 API calls behind use-case boundaries:

```
Task<UploadInitResult>   InitiateUploadAsync(fileName, contentType, fileSize, userId);
Task<UploadCompleteResult> CompleteUploadAsync(uploadId, parts);
Task<Uri>                 GetDownloadUrlAsync(objectKey);
Task                      DeleteObjectAsync(objectKey);
```

`[ADOPTED]`

### AD-6 — Download via 302 redirect

- **Binds:** CAP-2
- **Prevents:** Server proxying file bytes, consuming bandwidth
- **Rule:** `DownloadDeliveryHandler` calls `GetDownloadUrlAsync()` → returns 302 redirect to R2 signed URL (60s TTL). Zero server egress. `LocalDiskProvider.GetDownloadUrlAsync()` throws `NotSupportedException`. `[ADOPTED]`

### AD-7 — Delivery.StoragePath + R2Options config

- **Binds:** CAP-4, CAP-6
- **Prevents:** Ambiguity between local-disk and R2 deliveries at read time; write-timing confusion
- **Rule:** New `Delivery.StoragePath` (nullable string) stores full R2 object key. Written by `CompleteR2UploadHandler` after successful R2 verification + `CompleteMultipartUploadAsync` — never at start time. Null = local disk backward compat. Config section renamed to `R2Options`. `[ADOPTED]`

### AD-8 — Cost-optimal design principle

- **Binds:** all
- **Prevents:** Redundant verification rounds, unnecessary round-trips
- **Rule:** Every flow is designed for minimum bandwidth/cost. CompleteUploadAsync calls `CompleteMultipartUploadAsync` directly (no `ListParts` pre-check — R2 validates). Single-PUT uses `HeadObjectAsync`. `[ADOPTED]`

### AD-9 — AES-256-GCM encryption at rest (automatic)

- **Binds:** CAP-1, CAP-2
- **Prevents:** Operator key management overhead
- **Rule:** R2 transparently encrypts all objects at rest using AES-256-GCM. No SSE headers needed — encryption is always-on, automatic, zero config. R2 does NOT support the `x-amz-server-side-encryption` request header (AWS SSE-S3). Client-side PIN encryption (existing) is an independent layer. `[ADOPTED]`

### AD-10 — uploadId lifecycle: R2 multipart UploadId persisted in UploadSession

- **Binds:** CAP-1, CAP-3, CAP-5
- **Prevents:** Start→Commit coupling failure; R2 multipart UploadId loss between handlers
- **Rule:** `uploadId` returned by `InitiateUploadAsync` is the R2 multipart upload ID string. `StartR2UploadHandler` stores it in `UploadSession.R2UploadId` (new column). `CommitR2UploadHandler` reads it from the session and passes it to `CompleteUploadAsync`. This avoids ambiguity between R2's upload ID and the application's session ID. `[ADOPTED]`

### AD-11 — Error handling: fail-fast, no fallback

- **Binds:** CAP-1, CAP-2, CAP-3, CAP-5
- **Prevents:** Silent failures; inconsistent error responses; accidental fallback to local disk which would proxy bytes
- **Rule:** `R2StorageProvider` throws `R2StorageException` (wrapping `AmazonS3Exception`) on all R2 API failures. Handlers catch it and return appropriate HTTP status codes: 502 BadGateway for R2 unreachable / transient errors, 400 BadRequest for invalid commit data. No retry in handlers — `R2StorageProvider` may implement internal retry for transient S3 errors only. No fallback to local disk — if R2 is down, upload/download returns 502. `[ADOPTED]`

## Consistency Conventions

| Concern | Convention |
| --- | --- |
| Upload endpoint naming | Local: `/api/uploads/start` / `{id}/chunks` / `commit`. R2: `/api/uploads/start-r2` / `commit-r2` |
| Download endpoint | Shared: `GET /api/downloads/{code}` — handler routes based on `Delivery.StoragePath` |
| R2 object key format | `uploads/{userId}/{deliveryId}/{fileName}` — all lowercase, no trailing slash |
| Presigned URL TTL | Upload parts: 15 min. Download: 60 sec. |
| Multipart threshold | 10 MB (configurable via `R2Options.MultipartThreshold`) |
| AES-256-GCM encryption | Always-on, automatic, transparent — no SSE headers passed |

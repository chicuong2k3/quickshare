topic: Cloudflare R2 blob storage integration
updated: 2026-07-20T23:25
---

- (direction) User wants Cloudflare R2 blob storage integration to reduce server bandwidth for self-hosting at home.
- (constraint) Server must serve only as control plane (metadata + signed URLs), never proxy file bytes through server.
- (constraint) R2 has /TB egress — remove all server-side bandwidth cost for file delivery.
- (constraint) Must use existing IStorageProvider interface — R2StorageProvider implements same contract as LocalDiskStorageProvider.
- (capability) CAP-1: Presigned upload URL generation — client uploads chunks directly to R2 via PUT presigned URLs, server never sees file bytes.
- (capability) CAP-2: Presigned download URL — download requests redirect to signed R2 URLs, zero egress through server.
- (capability) CAP-3: S3-compatible multipart upload for large files (>100MB) with presigned part URLs.
- (capability) CAP-4: Encrypted file storage at rest — server encrypts before uploading to R2, decrypts when serving signed download URLs (or client-side encryption).
- (capability) CAP-5: Storage backend switchable via config — R2 or local disk, zero code change when switching between environments.
- (capability) CAP-6: Server verifies upload completion via HEAD/ListParts on R2 before creating Delivery record.
- (direction) Existing chunked upload flow (StartUpload → Chunks → Commit) is rewritten: StartUpload generates signed URLs, Chunks are PUT directly to R2 by client, Commit verifies via R2.
- (decision) AWSSDK.S3 NuGet package for R2 S3-compatible API access.
- (decision) R2 config stored in appsettings.json under R2: section (AccountId, Bucket, AccessKey, SecretKey, PublicUrl).
- (non-goal) Not replacing or modifying P2P transfer path — P2P remains direct peer-to-peer.
- (non-goal) Not migrating existing uploads (Delivery records with local disk paths) — backward compat handled at migration time, not in this spec.
- (non-goal) Not adding CDN layer on top of R2 — R2's own global network is sufficient.
- (event) Self-validate Pass 1 (Coherence): PASS — all 6 Spec Law rules satisfied. Each capability has intent+success, no HOW in intents, constraints are binding, 4 non-goals explicit, success signal testable, IDs unique.
- (event) Self-validate Pass 2 (Preservation): PASS — all 16 source claims from memlog land in SPEC.md kernel or companions. Single open question recorded (SSE-S3 vs SSE-C).
- (decision) SSE-S3 chosen for encryption at rest (open question resolved). Rationale: automatic, free, AES-256-GCM, zero config overhead. Client-side PIN encryption already covers use case where operator cannot trust Cloudflare.

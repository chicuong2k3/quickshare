- (decision) AD-1 [ASSUMPTION]: P2P-First with Upload Fallback — sender creates share link while online (connected to WebSocket). When receiver opens link and sender is online, P2P transfer begins immediately. If sender is offline, existing server-based delivery is shown. Prevents: dual-link confusion, unnecessary uploads when P2P succeeds.
- (decision) AD-2: Signaling via raw ASP.NET Core WebSocket middleware — lightweight, no extra package (SignalR is overkill for simple SDP/ICE relay). Server tracks sender WebSocket connections per share-link ID. Prevents: signaling dependency bloat, unnecessary reconnection complexity.
- (decision) AD-3: Online detection via WebSocket presence — sender connects to signaling WebSocket upon creating a share link. Server stores sender's connection status keyed by share-link ID in memory (ConcurrentDictionary). When receiver opens the link, server checks presence: online → trigger P2P handshake, offline → serve server-based page. Prevents: polling overhead, complex presence infrastructure.
- (decision) AD-4: Chunked DataChannel transfer with bufferedAmount backpressure — chunk size 16KB (WebRTC SCTP recommended). Sender monitors bufferedAmount, pauses when >1MB. Receiver reassembles chunks via Blob parts in memory (bounded by available RAM) or StreamSaver for disk streaming. Prevents: sender OOM from unbuffered sends, receiver memory exhaustion.
- (decision) AD-5: PIN-based E2E encryption for P2P — AES-256-GCM applied client-side before DataChannel send, key derived from user-entered PIN via PBKDF2. PIN never sent over signaling or WebSocket. Receiver must enter PIN to derive key and decrypt. Without PIN, DTLS transport encryption alone applies. Extends parent AD-15 zero-knowledge philosophy with different key delivery (PIN vs fragment). Prevents: server-side PIN verification leakage, PIN-in-transit interception.
- (decision) AD-6: P2P does not use IStorageProvider — file never touches server storage. Zero server egress cost. For free-tier ads (inherited AD-18), the P2P download page still renders ads via the same ad-injection mechanism. P2P delivery complete notification sent via WebSocket to server for analytics tracking (optional, non-blocking). Prevents: unnecessary storage egress, storage provider coupling for P2P path.
- (decision) AD-7 [ASSUMPTION]: File access via File API + chunked FileReader — sender selects file via <input type=file>. File is read in 16KB slices using FileReader API. Sender must keep browser tab open for entire transfer duration. Prevents: File System Access API complexity, cross-browser compatibility issues (File API is universally supported).
- (direction) Paradigm: Blazor SSR + FastEndpoints + Wolverine with WebRTC P2P delivery channel — inherits existing system paradigm, adds real-time signaling layer
- (direction) Inherited invariants from parent spine: AD-1 (IStorageProvider), AD-2 (Chunked Upload Flow), AD-6 (Entity Model), AD-15 (Client Encryption for server files), AD-16 (Download Count Cap), AD-17 (Egress Accounting), AD-18 (Ad Injection), AD-19 (Access Control), AD-21 (Anti-Adblock) — all fully binding for server fallback path
- (direction) Deferred: Optimal chunk size for DataChannel requires production benchmarking (16KB starting point). STUN/TURN server selection (Google public STUN free, TURN needs self-host or third-party). Concurrent P2P transfer limits per-tier (Free/Starter/Ultimate) deferred to implementation.
- (decision) AD-1 revised: Fallback model = upload-on-demand (option b2). Sender keeps tab open (background). If P2P fails while sender connected, server notifies sender via WebSocket → sender uploads in-page → receiver downloads via server. If sender already disconnected, no fallback. P2P timeout: ICE 30s, DataChannel 10s.
- (fix) Review fixes applied: AD-1a (P2P share-link creation flow), AD-2 protocol (role field + file-meta message), AD-3 (P2PRoom 1:1 model + rate limiting), AD-4 (StreamSaver mandatory for >500MB), AD-5 (PIN vs fragment key separation), deferred (multi-receiver).
